# Протокол EpicPlayer

Спецификация проводного формата между приложением и устройством шоу.
Источник: разбор `EpicPlayer/MainWindow.xaml.cs`, `WifiDevicesWindow.xaml.cs`,
`WifiTcpDevicesWindow.xaml.cs`, `ViewModel/WifiInfoDevice.cs`.

**Назначение документа.** Windows- и macOS-реализации развиваются независимо,
поэтому этот файл — контракт между ними. Расхождения в формате пакетов
проявятся только на шоу, в худший момент. Формат зафиксирован здесь,
изменения требуют синхронного обновления обеих реализаций.

Всё ниже помечено `[из кода]` — выведено из поведения клиента,
или `[проверить]` — требует подтверждения на реальном устройстве.

## 1. Каналы

| Канал | Порт | Режим | Назначение |
| --- | --- | --- | --- |
| UDP | 333 | broadcast | команды воспроизведения, device lookup |
| UDP | 6454 | unicast + broadcast | Art-Net (DMX), независим от протокола |
| TCP | эфемерный | по инициативе устройства | device lookup, канал управления |

Приложение само биндится на UDP 333 (`MainWindow.xaml.cs:122`), то есть
слушает тот же порт, в который шлёт. Ответы устройств приходят на 333.

Адрес назначения вычисляется из выбранного интерфейса: последний октет
IP заменяется на 255. Маска подсети при этом игнорируется — см.
[Известные расхождения](#известные-расхождения).

## 2. Команда воспроизведения — 8 байт

Основной пакет. Отправляется на broadcast:333 `[из кода]`

| Смещение | Размер | Значение |
| --- | --- | --- |
| 0 | 1 | `0x50` |
| 1 | 1 | `0x05` |
| 2 | 1 | команда |
| 3–6 | 4 | позиция, мс, **little endian** |
| 7 | 1 | `0x0D` |

### Команды

| Код | Действие |
| --- | --- |
| `0x02` | play |
| `0x03` | pause |
| `0x04` | stop |
| `0x05` | следующий трек |
| `0x06` | предыдущий трек |

### Позиция

Передаётся вместе с play, pause и stop. Для next и previous отправляется 0 —
устройство само решает, что значит «следующий» для шоу.

Важно: порядок байтов little endian. В .NET это даёт `BitConverter.GetBytes`
как побочный эффект архитектуры x86; **в Swift endianness задаётся явно**.
x86 и arm64 оба little endian, так что на текущих машинах ошибка не
проявится, но формат не должен зависеть от архитектуры.

### Периодическая отправка позиции

**Раз в секунду** во время воспроизведения. Решение владельца проекта,
совпадает с фактическим поведением Windows-версии.

README Windows-версии обещает интервал в 5 секунд — это известная
ошибка документации, см. [Известные расхождения](#известные-расхождения),
пункт 1. Каноническое поведение задано здесь: **1 секунда**.

На длинных треках это около 1 пакета в секунду, что приемлемо для UDP
и не создаёт заметной нагрузки.

### Повтор stop в остановленном состоянии

Пока плеер остановлен, Windows-версия раз в секунду шлёт stop с позицией 0
(`StopTimerCallback`, `MainWindow.xaml.cs`) `[из кода]`. Пауза
не повторяется. Во время открытого окна device lookup повтор отключён
(`_suppressPlaybackCommands`). Устройство, видимо, на это рассчитывает:
пропущенный stop досылается без участия оператора.

### Команда одному устройству

Из окна device lookup команды play, pause и stop уходят unicast на адрес
устройства, порт 333 (`WifiPort`), позиция всегда 0
(`WifiInfoDevice.cs`) `[из кода]`.

## 3. Device lookup, UDP — 3 байта

Запрос отправляется на broadcast:333 при открытии окна и по кнопке Refresh `[из кода]`

```
0x49 0x00 0x0D
```

## 4. Device lookup, TCP — 9 байт

Отправляется на broadcast:333 при открытии TCP-окна `[из кода]`

| Смещение | Размер | Значение |
| --- | --- | --- |
| 0 | 1 | `0x4C` |
| 1 | 1 | `0x06` |
| 2–5 | 4 | адрес отправителя |
| 6–7 | 2 | TCP-порт отправителя, little endian (`3331`) |
| 8 | 1 | `0x0D` |

Устройство читает адрес и порт, затем подключается TCP-клиентом на указанный
порт. Приложение принимает соединение и отвечает на **тот порт, с которого
пришло соединение** — то есть управление идёт обратно по эфемерному порту,
а не на фиксированный `3331`.

## 5. Ответ устройства

Формат изучен частично `[проверить]`

| Что известно | Источник |
| --- | --- |
| Первый байт `0x49` | `WifiDevicesWindow.xaml.cs:83` |
| Длина больше 3 байт | там же |
| Имя устройства — байты 47–58, 12 байт | `WifiInfoDevice.cs:51` |
| Кодировка имени — Windows-1251 | там же |
| Хвост строки добит нулями, они обрезаются | там же |

Остальной формат ответа не используется приложением и не документирован.
Разбор при необходимости — reverse engineering на реальном устройстве,
именно здесь понадобится захват трафика (`tcpdump`).

Приложение показывает и «сырой» ответ целиком в hex (`RawData`), что
пригодилось бы при разборе.

## 6. Art-Net — 6454

Штатный протокол, реализация в `eDmx.ArtNet`. Совместимость с macOS
не требует правок — библиотека использует только `System.Net.Sockets`.

Приложение подписывается на DMX и реагирует на **изменение** значения
канала, а не на само значение: удержание кнопки на пульте не перезапускает
трек. Значения по умолчанию — 50 play, 100 pause, 150 stop.

Приложение только слушает и не отправляет DMX.

## Известные расхождения

Расхождения между README и кодом. Зафиксированы, чтобы при переносе
не выбрать поведение по ошибке. Ничего не исправлено — поведение Windows
версии менять нельзя без синхронизации с устройством.

1. **Периодическая отправка позиции.** README Windows-версии: «каждые
   5 секунд». Код (`MainWindow.xaml.cs:326`): условие
   `timepoint - _lastMsSent > 5000`, при этом `_lastMsSent` не
   обновляется после отправки и равен 0. Значит после первых 5 секунд
   воспроизведения пакет уходит **каждую секунду** (тик `songTime`),
   а не раз в пять. **Решено:** каноническим считается интервал
   1 секунда, именно его реализует macOS-версия. Расхождение с README
   Windows-версии остаётся и здесь его нужно будет поправить.

2. **Broadcast не учитывает маску.** Адрес строится заменой последнего
   октета на 255 (`MainWindow.xaml.cs:200`), предполагается /24. Для сети
   192.168.88.0/24 корректно, для 192.168.0.0/16 — нет.
   Поле multicast сохраняется, но скрыто и не используется.

3. **Гонка общих буферов.** Пакеты собираются в полях `_playBytes`,
   `_stopBytes` и т. д., которые мутируются из UI-потока и из
   threadpool-таймеров одновременно. На практике воспроизводится редко,
   но гонка настоящая: **в Swift выделять буфер на каждый send**.

4. **Art-Net: адрес от отправителя.** В TCP-пакете (раздел 4) в байты 2–5
   кладётся адрес из `IPEndPoint`, который в `MainWindow` уже является
   broadcast-адресом (`x.x.x.255`), а не адресом самого компьютера.
   Выглядит как ошибка, но может быть согласовано с прошивкой устройства.
   `[проверить]` — на живом устройстве.

5. **Обход от переполнения.** `UInt32 timepoint - _lastMsSent` при перемотке
   назад даёт подпоток и условие всегда истинно. В Swift проверять явно.

6. **TCP device lookup в Windows-версии не работает.** В
   `WifiTcpDevicesWindow` поля `_devices` и `_devicesDictionary` не
   инициализированы: конструктор падает на `Devices.CollectionChanged`
   до отправки 9-байтового пакета. `TcpListener` не создаётся вообще.
   Значит, раздел 4 на устройстве никогда не проверялся, и формат
   объявления — только вывод из кода. `[проверить]`

7. **Настройка Universe не применяется.** Windows-версия сохраняет
   Universe, но реагирует на DMX с любого universe. При двух потоках
   с разными значениями канала команды будут срабатывать постоянно.
   macOS-версия по умолчанию повторяет это (`universe: nil`), фильтр
   включается настройкой.

8. **Art-Net биндится на IP из настроек.** На Windows такой сокет
   получает и broadcast, на macOS — нет. macOS-версия слушает
   `0.0.0.0` с привязкой к интерфейсу.

## Порядок реализации

Протокол логично реализовать первым, до UI, и проверять на железе:

1. Отправка 8-байтового пакета, подтверждение реакции устройства.
2. Device lookup по UDP — проверка появления устройства в списке.
3. Device lookup по TCP — проверка соединения.
4. Приём Art-Net и реакция на DMX.

Пункты 1 и 2 проверяются одним устройством за одну сессию и дают
уверенность, что канал работает, до написания интерфейса.
